# Atmel AT28C16 on PicProg+ 2.77

Select `AT28C16,P` for the normal 2,048-byte EEPROM array. For example, with
an existing writable 2 KiB virtual chip and a three-byte payload:

```sh
make dos lab
python3 tools/rf5_client_lab.py chip.bin WRITE payload.bin --library /path/to/Core/picprog.lib --profile AT28C16,P --start 17 --length 3
python3 tools/rf5_client_lab.py chip.bin READ dump.bin --library /path/to/Core/picprog.lib --profile AT28C16,P
make parity-at28c16 CORE=/path/to/Core
```

In DOS the write is `PICRF5 WRITE IMAGE.BIN 378 PICPROG.LIB 17 3 AT28C16,P`.
The selected profile explicitly supplies the socket type to the lab. A 2 KiB
file without that selection retains its previous EPROM behavior. The user's
library supplies the third configuration stream (offset 19490, 2778 bytes,
CRC32 6670671E). The virtual programmer recognizes that streamed configuration
and answers with ID 13h. No vendor bitstream is distributed.

**Use WRITE to replace bytes.** Both clients can write 00h and subsequently
FFh at the same address. Phyton's OVERWRITE preflight still rejects a
0→1 transition before programming. READ, CHECK (blank), VERIFY, WRITE and
OVERWRITE were compared against the original. The two clients also persisted
and cross-read each other's writes in separate DOS sessions.

The original latches outgoing data, drives register 4 low, sets register 6
to 2, releases register 4 to 2, then returns register 6 through 3 to 4.
The write routine and its byte polling loop start at DOS EXE file offsets
3264Fh and 326B7h. It polls the entire byte, then verifies it again.
The virtual cell latches the address and data on successive qualified edges.
While busy it returns complemented D7 and variable low bits. A completed write
replaces the addressed byte; it does not clear bits by AND as on the EPROM.
See the [Atmel AT28C16 datasheet, Device Operation](https://ww1.microchip.com/downloads/en/DeviceDoc/doc0540.pdf).

The lab uses completed byte samples instead of elapsed milliseconds:
`PP_EEPROM_BUSY=0` completes immediately, a positive count returns that many
busy samples, and `never` keeps the cell busy and leaves the backing byte
unchanged. Both DOS programs abandon a never-ready cell after two BIOS tick
transitions. Faster code can take more samples within the same deadline;
the timeout test compares the entry, each busy sample and shutdown, allowing
only the repeat count to differ. All finite-delay comparisons require exactly
the same number and ordering of LPT events. This is digital protocol evidence;
socket voltages, edge timing, the high-voltage identification area and chip
clear are not modeled or validated.

At the ppdev boundary the full-array READ, blank CHECK and VERIFY fixtures
each matched 356,156 events. The 257-byte WRITE at 00FFh matched 353,739
events with two busy reads per changed byte; OVERWRITE matched 358,467 with
three. The first and last cell were also written separately. In the
never-ready test both clients reported failure at 0011h, did not alter the
image, and produced the same shutdown sequence.

For an end-to-end DOSRAVI check, run
`bash tests/dosravi-smoke.sh --at28c16 /path/to/Core`.
This stages the library on the temporary DOS drive, uploads the independent
client and a 2 KiB payload, programs the virtual EEPROM on an emulated 8086,
then retrieves and compares the entire dump in a second session.
